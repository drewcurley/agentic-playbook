# T-009.1 — `verify` entrypoint, pinned toolchain, shared helpers

## Description
Today the procedure gates, shellcheck and three fixture suites are separate steps hard-coded in `azure-pipelines.yml` (and duplicated in the parked Actions workflow). An agent has no single command that means "done", and a project's own lint/type/test steps have nowhere standard to plug in.

Deliver `scripts/verify.sh [<base-ref>]`: it runs every executable stage in `scripts/verify.d/` in one lexical order and writes a summary. Stage exit codes: `0` PASS, `77` SKIPPED, `78` N/A, anything else FAIL. **Stage number ranges:** `00–29` core checks, `30–69` adopter stages (lint, types, tests), `70–99` evidence stages (contracts, trace, review) — so evidence stages always run after the tests that produce their inputs. Core stages are listed in `scripts/verify.d/core.manifest`; in CI, `verify.sh` itself, the manifest and every core stage and helper come from a BASE gate snapshot (ADR 0003, gate integrity). **CI mode** means `CI=true`, `TF_BUILD=True` or `GITHUB_ACTIONS=true` (Azure DevOps sets only `TF_BUILD`); every "in CI" rule below applies in CI mode. Mechanics are documented in `scripts/verify.d/README.md`; `AGENTS.md` carries pointers only.

This task also ships the shared helpers later subtasks depend on: JUnit emitter, log sanitiser, portable timeout, the `assert_suite` doc-assertion helper, and the reason-code table.

## Acceptance criteria
- [ ] **AC-T009.1-01** — Given no argument, when `verify.sh` runs locally, then `BASE` resolves to `git merge-base HEAD origin/main`, falling back to `main` with a printed warning, and the resolved `BASE...HEAD` range is printed. Given CI mode and an unresolvable base, then it fails with reason `BASE_UNRESOLVED` and `Fix: fetch the target branch (checkout fetchDepth: 0)` — never falling back to the root commit. In CI mode, `BASE_GATE` resolves from `refs/remotes/origin/<target>` as fetched at checkout (no fetch after checkout), and `VERIFY_PHASE` and `VERIFY_TODAY` are rejected (`TEST_ONLY_VAR_IN_CI`). One fixture per CI-mode variable.
- [ ] **AC-T009.1-02** — Given stages `10-a.sh` and `40-b.sh`, when `verify.sh` runs, then they execute in lexical order (`LC_ALL=C`), each receives `BASE`, `BASE_GATE`, `HEAD`, `VERIFY_REPORT_DIR` and `VERIFY_GATE_DIR`, and `scripts/verify.d/README.md` documents the 00–29 / 30–69 / 70–99 ranges. In CI, a working-tree stage with the same file name as a core stage is ignored in favour of the BASE copy (reported as `SHADOWED`).
- [ ] **AC-T009.1-03** — Given any stage exits with a code other than 0, 77 or 78, then `verify.sh` still runs every remaining stage and exits 1; given every stage exits 0, 77 or 78, then it exits 0.
- [ ] **AC-T009.1-04** — Given a run, then the terminal summary is one ASCII line per stage in execution order, `<RESULT>  <stage-name>  [(<reason>)]`, where `RESULT` ∈ `PASS FAIL N/A SKIPPED SHADOWED` and the reason is the stage's last stdout line prefixed `REASON:`, sanitised and truncated to one line. A 77/78 exit without a `REASON:` line is `FAIL (no reason given)`. Colour is used only when stdout is a TTY, `NO_COLOR` is unset and not in CI mode; the status word is always present. A fixture asserts no `\x1b` byte in output in CI mode; the TTY branch is tested deterministically via an injected `VERIFY_ASSUME_TTY=1` (itself rejected in CI mode). The same rows are written to `$VERIFY_REPORT_DIR/summary.tsv`.
- [ ] **AC-T009.1-05** — Given any stage reports FAIL, then each failing item is printed as `FAIL <item>: <REASON_CODE> — <detail>` followed by a `Fix: <command or doc anchor>` line, and every reason code is listed with its remedy in `scripts/verify.d/README.md`. This applies to every stage in T-009; each subtask's fixture suite asserts it for every FAIL its fixtures can trigger.
- [ ] **AC-T009.1-06** — Given a run, then `verify.sh` writes `$VERIFY_REPORT_DIR/summary.md`: first line is the overall result; then the stage table; then any `BOOTSTRAP` notices; then every `$VERIFY_REPORT_DIR/summary.d/<stage>.md` section a stage contributed, in stage order. Both CI definitions publish it and the rest of `$VERIFY_REPORT_DIR` as a build artifact with `condition: succeededOrFailed()` and a name suffixed with the job attempt (`$(System.JobAttempt)`), so re-runs don't collide. Under Azure DevOps each FAIL is also emitted once as `##vso[task.logissue type=error]` (sanitised) so it appears in the run summary. When `TF_BUILD` is set, each stage's output is wrapped in `##[group]`/`##[endgroup]` emitted by `verify.sh` after sanitising.
- [ ] **AC-T009.1-07** — Given CI mode in a pull-request build, then the pipeline step does not execute the working tree's `verify.sh`: it writes `verify.sh` from `BASE_GATE` (the target branch tip) to a temp dir and runs that copy (if `git cat-file -e "$BASE_GATE:scripts/verify.sh"` fails — bootstrap — the YAML step itself prints `BOOTSTRAP: verify.sh loaded from HEAD`, also runs `BASE_GATE`'s existing `scripts/ci-checks.sh` directly, and then runs `HEAD`'s copy); if the admin-only pipeline variable `VERIFY_GATE_REF` is set, it replaces `BASE_GATE` as the snapshot source (AC-T009.1-18); that copy extracts a **BASE gate snapshot** (`scripts/`, `.claude/agents/`, `review-scope.conf`, `tool-versions.lock`, `contracts/adapters/` — each path first checked with `git cat-file -e`, then `git archive "$BASE_GATE" <paths> | tar -x` into `VERIFY_GATE_DIR`) and runs the manifest, every core (gate) stage, and every script they invoke or source from that dir. Stages run against a worktree of the PR source commit (`System.PullRequest.SourceCommitId`, present locally as a parent of the merge ref), so stage results and T-009.4 hashes refer to the same commit. A manifest entry missing from `BASE_GATE` fails, unless `BASE_GATE` has no `core.manifest` (bootstrap), in which case `HEAD`'s copies run and the summary prints `BOOTSTRAP: gates loaded from HEAD`. Fixture PRs that edit `verify.sh`, a core stage, `scripts/ci-checks.sh` or `scripts/lib/sanitize.sh` to `exit 0` still fail on the base versions.
- [ ] **AC-T009.1-08** — Given the existing checks, then `core.manifest` lists **gate stages only** — procedure checks (`ci-checks.sh`) and shellcheck, plus the evidence stages added by later subtasks. The starter's own suites (`scripts/test/*.sh`) are **not** core: they run from the working tree as stage `40-starter-tests.sh` against working-tree scripts, so a PR's changes are actually tested, and the BASE-loaded trace stage (T-009.3) judges their JUnit. A fixture runs every previously-failing `test-ci-checks.sh` case through `verify.sh` and asserts it still fails (no gate dropped); converted legacy-suite cases cite AC-T009.1-08.
- [ ] **AC-T009.1-09** — Given `azure-pipelines.yml` and `.github/workflows-disabled/checks.yml`, then:
  - the `verify` job has one gate step (run BASE `verify.sh`), uses `checkout` with `fetchDepth: 0` and no `persistCredentials`, maps no secret variables, and sets `timeoutInMinutes`; each stage is bounded by `VERIFY_STAGE_TIMEOUT` (default 1800 s) via `scripts/lib/timeout.sh`;
  - the pipeline ends in a single `gate` job (`dependsOn` every other job, `condition: always()`) that fails if any dependency failed or was skipped other than the allowed skips — the review job when disabled or on a fork PR, and the PR-body job on non-PR builds (a fixture per allowed and disallowed skip) — `gate` is the **only** required status check;
  - the YAML defines no `variables:` entry for `REVIEW_REQUIRED` or `VERIFY_GATE_REF` (a fixture asserts this), because YAML variables override pipeline-level ones;
  - in non-PR builds (`Build.Reason` ≠ `PullRequest`, e.g. the `main` trigger), `BASE` is `HEAD^1` (the empty tree if `HEAD` has no parent), gates load from `HEAD` (main is trusted post-merge), and evidence and review stages report `N/A (post-merge)` so `main` does not go red after every merge;
  - in PR builds `HEAD` is the PR source commit (`System.PullRequest.SourceCommitId`), not the synthetic merge commit;
  - all stage output passes through `scripts/lib/sanitize.sh` with each stage's exit code captured via a file (no reliance on `pipefail`);
  - the PR-body check is a **separate job**, BASE-loaded, with `GITHUB_TOKEN` mapped only there, reporting `SKIPPED (no GITHUB_TOKEN)` when absent; inside `verify.sh` its stage always reports `SKIPPED (runs in isolated job)`;
  - the parked Actions workflow mirrors this with `permissions: contents: read`, `persist-credentials: false`, and a review-job condition excluding forks; a fixture asserts both CI definitions declare the same job names and entry points.
- [ ] **AC-T009.1-10** — Given `tool-versions.lock` with one row per tool and platform (`name version platform https-url sha256 license source`; platforms `linux-x86_64`, `linux-arm64`, `darwin-x86_64`, `darwin-arm64`) and a host allowlist in the same file, when `scripts/verify-bootstrap.sh` installs a tool, then a preflight first fails by name if any floor tool (`sh git awk jq tar xz gzip curl` and a sha256 tool) is missing; it rejects non-HTTPS URLs and non-allowlisted hosts; verifies the sha256; and fails closed on mismatch or on a missing platform row. Downloads go through `curl`, which fixtures replace with a stub on `PATH` (no network). A checksum-mismatch FAIL says `Fix: do not edit tool-versions.lock to match — report to the gate owners`. The apt fallback for shellcheck is removed. Fixtures prove tampered-checksum, missing-platform, disallowed-host and missing-floor-tool all fail, and one positive case proves a matching checksum installs the tool.
- [ ] **AC-T009.1-11** — Given `.devcontainer/devcontainer.json`, then it uses no devcontainer features, its `image` is pinned as `<image>@sha256:<digest>` (a glibc-based image providing `useradd`, `groupadd` and `sudo`, as Azure DevOps container jobs require — e.g. `mcr.microsoft.com/devcontainers/base`), and `postCreateCommand` runs `verify-bootstrap.sh`; both CI definitions run the `verify` job with `container:` set to the same `image@sha256` and run `verify-bootstrap.sh` as an explicit step. A fixture asserts the three digests are identical.
- [ ] **AC-T009.1-12** — Given `verify.sh` starts, then it empties `$VERIFY_REPORT_DIR` (default `.verify/reports`, gitignored) before any stage runs, so stale reports never count as evidence. Given `verify.sh` is invoked inside a running `verify.sh` with the same report dir, then it fails with `REPORT_DIR_NESTED`. Every fixture sets `VERIFY_REPORT_DIR` and its `tasks/` dir to `mktemp` directories, so fixture JUnit (which deliberately contains failing or unknown AC IDs) never reaches the real report dir.
- [ ] **AC-T009.1-13** — Given `scripts/lib/junit.sh`, when a shell suite sources it and records cases, then it writes valid JUnit XML to `$VERIFY_REPORT_DIR` with XML-escaped names; the three existing suites are converted to it.
- [ ] **AC-T009.1-14** — Given `scripts/lib/sanitize.sh`, when text containing `##vso[` or `##[` passes through it, then those sequences are neutralised; a fixture proves an injected `##vso[task.setvariable …]` prints inert. Given `scripts/lib/timeout.sh <seconds> <cmd…>`, then it kills the command and exits 124 on expiry, on both GNU and BSD userlands, including with `timeout` and `gtimeout` absent from `PATH` (fixture). Given `scripts/lib/md.sh md_cell <text>`, then it escapes `|` as `\|`, turns newlines into `<br>` and strips trailing whitespace; `contracts-index.sh` (T-009.2) and `trace.sh` (T-009.3) use it rather than their own escaping.
- [ ] **AC-T009.1-15** — Given a project-provided stage dropped into `scripts/verify.d/` in the 30–69 range (e.g. `50-unit-tests.sh`), when `verify.sh` runs, then it is picked up from the working tree with no other configuration.
- [ ] **AC-T009.1-16** — Given `scripts/test/test-doc-assertions.sh` (grep-based, emits JUnit) and its `assert_suite <path>` helper (asserts a suite exists, is shellcheck-clean, names every case with a valid AC ID, and emits JUnit; fixtures prove it fails on a missing suite, a case with no AC ID, an invalid ID, and a shellcheck error), then the suite checks:
  - `scripts/verify.d/README.md` documents exit codes, ranges, reason codes and a worked drop-in stage;
  - `ADOPTING.md` gives an incremental ladder — (1) run `verify.sh`, (2) add stack stages + JUnit, (3) register contracts, (4) tune `review-scope.conf`, (5) enable independent review — explains extending the devcontainer image for a stack toolchain, and updates "Definition of enforced";
  - `README.md` Quickstart includes `sh scripts/verify.sh`;
  - `ADOPTING.md` and `docs/runbooks/ci-gate-recovery.md` contain the required-check migration and pin/revert/unpin steps (AC-T009.1-19, AC-T009.1-18);
  - `AGENTS.md` is at most 585 lines (545 today + 40), so mechanics stay in `scripts/verify.d/README.md` across all of T-009;
  - AC-T009-01 and AC-T009-02 (the AC-T009-03 case is added in the T-009.5 PR, when the § 8 labels it checks exist; until then each subtask's doc AC asserts only its own labels);
  - `assert_suite scripts/test/test-verify.sh` (this task's suite). Each later subtask adds its own `assert_suite` case and doc cases when it lands.
- [ ] **AC-T009.1-17** — `scripts/test/test-verify.sh` covers AC-T009.1-01 … 15 and 18 with deterministic fixtures — no network, no wall clock, each run under `env -i` with an explicit environment so a CI-mode or TTY host can't change results, with one fixture proving `CI=true` alone and `TF_BUILD=True` alone each enable CI mode — names every case only with the AC ID it verifies (fixture IDs in names are written so they do not match the ID regex), and is shellcheck-clean along with every helper.
- [ ] **AC-T009.1-18** — Given a gate merged to `main` that fails every PR, then recovery is possible without a bypass: an administrator sets the pipeline-level variable `VERIFY_GATE_REF` (not settable at queue time) to a known-good commit, the revert PR is judged under that pinned gate, and the variable is cleared after merge. While pinned, the YAML step prints `PINNED: gates from <sha>` and the summary repeats it; a ref that is not an ancestor of the target branch fails with `GATE_REF_INVALID`; the runbook limits a pin to 24 h, renewable once with an incident-log entry, after which it escalates to the gate owners. Fixtures assert `PINNED: gates from <sha>` appears in both the step output and the summary, and that a non-ancestor ref fails with `GATE_REF_INVALID` and its `Fix:` line. `docs/runbooks/ci-gate-recovery.md` documents pin, revert, unpin and the required-check migration (AC-T009.1-19). A fixture merges an everything-fails gate, then proves a revert PR passes under the pin. Additionally, a PR touching any gate-class path (T-009.4 AC-06) also runs `HEAD`'s `verify.sh` as a second gate step inside the credential-free `verify` job (no secrets, no persisted credentials), after the BASE step and with its own `VERIFY_REPORT_DIR`, which must pass too — so a gate that would brick `main` fails before it merges.
- [ ] **AC-T009.1-19** — Given an existing fork whose branch protection requires the old check names (`procedure checks`, `shell scripts`), then `ADOPTING.md` and the runbook give an ordered migration — let the new `gate` check report on a throwaway PR, add it as required, then remove the old required checks — and warn that removing the old jobs before requiring `gate` blocks every PR. Both documents also have gate owners subscribe to build-failure notifications for the `main` pipeline (a red `main` is the first signal of a broken gate) — verified by a `test-doc-assertions.sh` case.

## Out of scope
- Contract, traceability and review-evidence stages (T-009.2 / .3 / .4).
- Any stack-specific lint/test stage in the starter itself (adopters add those).
- Git hooks calling `verify.sh`.
- Caching or parallel stage execution.
- Windows outside WSL.

## Risks / dependencies
- First subtask; every other T-009 subtask is a stage of this and uses its helpers.
- **Size L (19 ACs).** Build as stacked, separately reviewable PRs; the first carries the gate-inventory fixture (AC-T009.1-08) so every later PR proves no gate was dropped. The build review artifact reports time-to-first-green on a fresh fork (Adopter-lens watch item).
- Enforcement-file change: the PR includes the before/after gate inventory (T-009 Risks).
- **Residual:** Azure DevOps reads the pipeline YAML from the PR head, so a PR could edit `azure-pipelines.yml` to skip the BASE `verify.sh`. That file is gate-class (Architect + DevOps + CODEOWNERS approval, T-009.4 AC-06); adopters with ADO "required template" checks should enable them. Stated in ADR 0003.
- Moving CI into a container image changes the runner environment; the gate-inventory fixture proves nothing regressed.
