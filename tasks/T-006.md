# T-006 — Shippable: adoption runbook + branch protection

## Description
Before shipping the starter to teams, close the gaps that let a fork *look* enforced while nothing actually gates `main`. Two deliverables: a single ordered adoption runbook (`ADOPTING.md`) and functional branch protection on this canonical template repo so it models the enforced state.

Root issue found at review time: `main` had **no branch protection**, **no active server-side CI** (GH Actions parked, Azure DevOps not wired), and **placeholder CODEOWNERS** — so every gate was advisory and a `--no-verify` push to `main` bypassed everything.

## Acceptance criteria
- [x] `ADOPTING.md` — ordered fork→enforced checklist (placeholders → hooks → ADO CI + branch-policy validation → branch protection → first session), with a "definition of enforced" checklist and the don't-brick-the-repo ordering warnings.
- [x] Branch protection applied to `main` on the canonical repo: PR required, ≥1 approval, admins included (no bypass), force-push + deletion blocked, conversation resolution required.
- [x] Protection set **functionally**: no never-reporting status check required and code-owner review NOT required yet (CODEOWNERS still placeholder here) — so the repo isn't bricked. ADOPTING.md tells forks to tighten both once CI + real CODEOWNERS exist.
- [x] README + AGENTS.md point to ADOPTING.md as the entry point for adopters.

## Out of scope (org infra / per-fork, documented in ADOPTING.md)
- Wiring the Azure DevOps pipeline + branch-policy build validation (per repo, needs an ADO project).
- Requiring the CI status check in branch protection — only possible after the check has reported once (chicken-and-egg, documented).
- Filling real handles into this template's CODEOWNERS (forks do this; the placeholder gate forces it).

## Notes
This repo now practices what it preaches: no direct pushes to `main`, no force-push, PR-based history. **Solo-repo reality:** required approvals are set to `0` because GitHub forbids self-approval (a 1-person repo can't satisfy ≥1). The PR + CI + no-force-push gates still apply; the human-approver gate activates when a second maintainer joins. Documented as a carve-out in `AGENTS.md` § 8 and `ADOPTING.md` step 5.
