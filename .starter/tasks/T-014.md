# T-014 — A PR can't loosen the CI gates it is judged by

## Description
T-013 follow-up 2 (Architect). A PR build runs the PR's own copies of everything that defines the procedure check: `scripts/ci-checks.sh`, `.placeholder-allow`, `.gitattributes`, and the pipeline YAML. So a PR, including one from a contributor's fork, can loosen the rules it is judged by, in the same PR, without anything looking like a CI change:
- edit a regex in `ci-checks.sh` so its own secret passes;
- add its own file to `.placeholder-allow`;
- mark a file `-diff` / `binary` in `.gitattributes`, so git prints "Binary files differ" and the secret scan never sees the content (T-013 follow-up 3; the same happens to a file containing a NUL byte).

The pipeline YAML itself can't be protected from inside the repo: Azure DevOps Build Validation (and GitHub's `pull_request` event) run the YAML from the PR. Human review of gate-file changes, required by branch protection, is the control for that; the repo's job is to (a) make every other bypass require a visible edit to the pipeline, and (b) route those edits to the people who own the gates.

Stacked on PR #4 (T-013), which rewrote the same files; rebased onto `main` once #4 merges.

## Acceptance criteria
- [x] Given a PR that edits `scripts/ci-checks.sh` to pass anything and adds a secret, when the PR build runs, then the check fails (the target branch's `ci-checks.sh` ran, not the PR's).
- [x] Given a PR that adds an unreplaced placeholder and allowlists that file in its own `.placeholder-allow`, when the PR build runs, then the check fails (the target branch's allowlist applied).
- [x] Given a PR that marks a file `-diff` (or `binary`) in `.gitattributes` and puts a secret in it, when the PR build runs, then the secret is caught; same for a file with a NUL byte. The pre-commit hook catches both as well.
- [x] A clean PR passes; a target branch with no `.placeholder-allow` means "nothing allowlisted"; a target branch with no `scripts/ci-checks.sh`, an unresolvable target, or a git error fails closed with a message.
- [x] Both pipelines run PR builds through `scripts/ci-pr-checks.sh` **taken from the target branch** (an identical "trusted-gate" block in both CI files, run by a test); the PR's own copy runs only while the target has none, with a warning. Push builds are unchanged. (Architect blocker, plan review)
- [x] `ci-checks.sh` and `pre-commit` run with `LC_ALL=C`, so `--text` on binary content doesn't make BSD sed/grep fail; a binary file under a UTF-8 locale still passes. (Backend blocker, plan review)
- [x] `CI_PLACEHOLDER_ALLOW` set but empty means nothing is allowlisted (no fallback to the PR's list); `ci-pr-checks.sh` reads target files only when `ls-tree` shows a regular file, and warns when the target's gate predates `CI_PLACEHOLDER_ALLOW`. (Data, Backend)
- [x] `.github/CODEOWNERS` routes every gate file to the devops team + security lead: `azure-pipelines.yml`, `.github/`, `scripts/ci-*.sh`, `.githooks/`, `.placeholder-allow`, `.gitattributes`. `CODEOWNERS` itself is allowlisted for placeholders (it is a template file).
- [x] `ADOPTING.md` § 4 says to land `scripts/` on `main` before requiring the check, and how to configure fork builds (no secrets, comment required, `persistCredentials` caveat). § 5 says what the repo can't do on its own (the PR's YAML defines the check; required code-owner review protects it; solo repos rely on the maintainer), that allowlist/gate changes apply one PR later, to drop the `CODEOWNERS` allowlist entry once filled in, and a break-glass for a broken gate on `main`. (DevOps)
- [x] (Architect + Data, build review) A filename can't make its placeholder be checked as another path, or as none: names are listed unquoted and split on newlines only, are never glob-expanded, and are read back as literal paths (`AGENT[S].md`, `:(top)x`, `café.md`, `a b.md`). A name git must still quote fails closed. A non-ASCII `/docs` name still needs consensus. Renames diff as delete + add (`--no-renames`).
- [x] (Architect re-check, build review) A filename is never code: the placeholder report no longer interpolates the name into a sed script, where GNU sed's `e` command would run `x#;e cmd;#` inside the trusted gate. It is printed as data; tested in both suites.
- [x] `AGENTS.md` § 7 says PR builds run the target branch's gate through `ci-pr-checks.sh`, and that a gate change applies from the next PR on.
- [x] New `scripts/test/test-ci-pr-checks.sh` plus new cases in `test-ci-checks.sh` / `test-pre-commit.sh`; every new case fails against the current scripts and passes after; wired into both CI configs; shellcheck clean; suites pass under dash.

## Plan
1. **`scripts/ci-checks.sh`**
   - `allow_file="${CI_PLACEHOLDER_ALLOW:-.placeholder-allow}"`, so a caller can supply a trusted allowlist. Default unchanged for local and push runs.
   - Content diffs get `--text --no-textconv --no-ext-diff`, so `.gitattributes` (`-diff`, `binary`, a textconv driver) and NUL bytes can't hide content from the scans.
2. **`.githooks/pre-commit`**: the same three flags on its content diffs.
3. **New `scripts/ci-pr-checks.sh <target-ref> <head-sha>`**: resolves the target to a commit, extracts the target's `scripts/ci-checks.sh` and `.placeholder-allow` into a temp dir, and runs that `ci-checks.sh` with `CI_PLACEHOLDER_ALLOW` pointing at the target's allowlist, against `<target-sha> <head-sha>`. `ci-checks.sh` diffs from the merge base, so the target tip is a correct base.
   - If the target has no `.placeholder-allow`, an empty allowlist is used. Presence is checked with `git ls-tree`, which tells "missing" apart from "git failed".
   - Fails closed if the target has no `ci-checks.sh`, the target doesn't resolve, or any git call errors.
4. **`azure-pipelines.yml`**, PR branch: `sh scripts/ci-pr-checks.sh "$(git rev-parse FETCH_HEAD)" "$head"`. **`.github/workflows-disabled/checks.yml`**, `pull_request`: same, with the base SHA from the event.
5. **`.github/CODEOWNERS`**: a "Gate files" block (placeholders, like the rest of the file). `/.github/` also gets the security lead. `.placeholder-allow` gets `.github/CODEOWNERS`.
6. **`ADOPTING.md` § 5**: a short "What CI can't protect on its own" note.
7. **Tests**
   - **New `test-ci-pr-checks.sh`**: fixture repos with a `main` carrying the real `ci-checks.sh` and a PR branch. Cases:
     - a clean PR passes;
     - a tampered `ci-checks.sh` plus a secret still fails;
     - a self-allowlisted placeholder still fails;
     - a target with no allowlist works;
     - a target with no `ci-checks.sh` fails closed;
     - an unresolvable target fails closed;
     - a git error fails closed (PATH stub);
     - a target argument that looks like an option is refused.
   - **`test-ci-checks.sh`**: `CI_PLACEHOLDER_ALLOW` is honoured; a `-diff` attribute, `binary`, or a NUL byte can't hide a secret.
   - **`test-pre-commit.sh`**: a `-diff` attribute and a NUL byte can't hide a secret.

## Risks / dependencies
- **Allowlist changes take effect one PR later.** A PR that adds a new placeholder-bearing template must land its `.placeholder-allow` entry first, or in an earlier PR. This is intended (a PR can't allowlist itself) and is documented in `ADOPTING.md`.
  - This PR is the exception: `main`'s `ci-checks.sh` predates `CI_PLACEHOLDER_ALLOW` and reads the working-tree allowlist, so the PR's own `CODEOWNERS` allowlist entry applies to it.
- **The PR's gate changes don't run on the PR itself.** Fixes to `ci-checks.sh` only take effect after merge. The fixture suites in the `scripts` job still test the PR's version.
- **`--text` on real binaries adds noise lines to the scanned diff.** That only means more content gets scanned. A binary that happens to contain a key-shaped byte sequence would now block, which is acceptable for a secret gate.
