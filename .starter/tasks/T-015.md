# T-015 — Keep the starter's own ledger out of adopters' tasks/ and docs/

## Description
The user reports: "When people are adopting this playbook they get confused on the existing task list, and sometimes the playbook itself gets caught up on the existing tasks." The starter ships two different kinds of task in one ledger:

- **Seeds for adopters** (`tasks/T-001`, `T-001.1`–`T-001.17`: the docs bootstrap; `T-002`: adopt the workspace model). These are template content. Every adopter should get them, still `proposed`.
- **The starter's own maintenance history** (`T-003`–`T-008`, `T-012`–`T-014`, and PR #2's `T-009`–`T-011`). This is how the template was built. It is not work the adopter owns.

`AGENTS.md` makes every session read `tasks/INDEX.md` first, so an adopter's agent treats our history as the project's own: it picks up our "completed" work, our follow-ups, and our IDs.

`/docs` has the same problem. `docs/decisions/0001-…` and `0002-…` and `docs/reviews/{feat-workspace-model,chore-ci-azure-devops}/` are the starter's own records. Every session reads all of `/docs`, and the Review Coordinator reads `/docs/reviews/` for past artifacts. An adopter's seeded `T-001.11` writes *their* ADR 0001, which collides with ours, and `T-001.12` builds `/docs/reviews/` fresh.

The user suggested `.gitignore`-ing our task list. **Kicked back:**
- Our own procedure needs task files committed: Task IDs reference them, PRs link them, review artifacts live in them, and completion happens in the work PR.
- A `.gitignore` line would ship to adopters and silently stop *their* tasks committing.
- Ignoring all of `tasks/` would also drop the seeds.
- Already-tracked files are unaffected anyway.

The user then delegated the design ("just use your best judgement").

## Decision (proposed)
- **Two committed ledgers.** The starter's own history moves to **`.starter/`**: `.starter/tasks/` and `.starter/docs/{decisions,reviews}/`. `tasks/` and `docs/` ship only what an adopter should start from.
- **Keep the `T-NNN` IDs.** The two ledgers never share a folder, so files can't collide. A different prefix would mean widening the commit-msg/CI Task-ID gate that every adopter relies on.
  - Cost: in a fork that syncs upstream, `git log --grep T-0NN` can also match upstream commits. This is documented.
  - Historic commits reference `T-003`… already, and can't be renamed anyway.
- **Onboarding:**
  - A repo created from the template (no upstream sync) deletes `.starter/` in its first PR.
  - A fork that pulls upstream updates **keeps** it. The procedure ignores it, and deleting it would cause a conflict on every sync.
- **Timing:** built now, stacked on #5 (it moves T-013/T-014). PR #2 (T-009–T-011, ADR 0003, a review artifact) is independent. Whichever of #2 and this lands second moves #2's files into `.starter/`.

## Seven lenses (`AGENTS.md` § 4; major decision: repo layout and onboarding flow)
1. **CEO.** This fits the strategy: the starter's value is a clean first run, and an adopter-reported confusion gets fixed. Story if it works: "fork it, and your agents start on *your* project". If it fails: little damage, and it's reversible. No internal political risk.
2. **Purchasing.** No cost and no vendor. Security posture is unchanged with one accepted trade-off: the starter's own ADRs and reviews leave the mechanically enforced `/docs` consensus gate. They are protected instead by `CODEOWNERS` (tech lead and architect) and a convention, and **accepted explicitly by the user on 2026-11-01** (escalated by the Review Coordinator). No new dependencies.
3. **Product/PM.** Buildable now: moves, docs, one test suite. Dependencies: the stack on #5 ← #4, and coordination with PR #2 (checklist posted). Scope-creep risk is the `/docs` part; it's included because the ADR-0001 collision makes a tasks-only fix incomplete (Analyst agrees). It's the right time: before more starter history piles up in `tasks/`.
4. **Adopter.** Less friction. A template user answers one question in `ADOPTING.md` § 1 and maybe runs one `git rm -r .starter`. A forker does nothing. Their agents stop treating our backlog as theirs. The cost: one more concept, "`.starter/` isn't yours", carried by banners and an `AGENTS.md` rule.
5. **Builder.** Mixed, and the main tension. Gains: a clean separation, history kept with `git mv`, and an enforced invariant instead of tribal knowledge. Costs maintainers pay indefinitely:
   - a seven-check shell test with its own `awk` path extractor and GitHub slug rules, which is real maintenance surface;
   - the "starter T-0NN" convention every future comment must follow;
   - the rule that whichever PR lands second moves PR #2's files.

   Mitigations: each check has its own fixture, so a failure points at one rule. Check 5 enforces the convention mechanically, so nobody has to remember it. The test is git-free and `find`-based, which keeps it portable. Would we be proud of it in a year? Yes, if the test stays small; anything beyond these seven checks should be pushed back on.
6. **Investor.** Time to first useful agent session is the starter's moat, and this improves it. No unit-economics impact. Execution risk is low; the change is mechanical.
7. **Marketing/Sales.** 60-second story: "Fork it, open your agent, and it starts building *your* docs, not reciting our changelog." The demo improves. Expected objection: "What's this `.starter/` folder?" Answer: the banner, plus "keep it if you'll pull updates, delete it if not". Before/after is clean.

**Lens conflicts:**
- **Builder vs. Adopter/Marketing.** The Builder carries a convention and a test so that adopters get a clean first run. Resolved: the convention is enforced by check 5 rather than by memory, and the test is fixture-per-check.
- **UX's "keep `.starter/` by default" vs. CEO/Marketing's "ships clean".** A kept `.starter/` means the template doesn't look clean. Resolved: the `AGENTS.md` rule and banners make a kept `.starter/` inert to agents, and only the human sees it, with an explanation. "Clean" means clean for the agents, which is what the reported problem was.
- **PM vs. Adopter on `/docs` scope.** Resolved toward inclusion.
- No unresolved red flag. The one gate trade-off (Purchasing) goes to the user.
