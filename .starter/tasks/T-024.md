# T-024 — Stop CI and the hooks echoing PR-controlled text, and scan every added line

## Description
The T-023 plan review (Architect and DevOps) found problems in existing code, and the owner asked to fix them here. This task's own plan review found one more: the worst of the set.

1. **Added lines starting with `++` are never scanned.** The Architect reproduced this.
   - `added_only` is `sed '/^+++/d'`, used in `scripts/ci-checks.sh` and `.githooks/pre-commit`. It drops every added line whose content starts with `++`, not just the `+++ b/file` header.
   - A commit adding a line that starts with `++` and holds an AWS-key-shaped string (`AKIA` plus 16 capitals) or a placeholder (`[insert`, a word, `here]`) passes both the placeholder and secret scans, in CI and in the hook.
2. **PR-controlled text reaches CI logs unchanged.** Azure DevOps acts on `##vso[…]` anywhere in a log line. GitHub Actions acts on `::command::` at the start of a line, after leading whitespace. `scripts/ci-checks.sh` prints three such things unchanged:
   - each placeholder hit's diff line;
   - each commit's subject (check 3);
   - file names in its messages. Git allows `#`, `[`, `:`, spaces and control bytes in names.
3. **The hooks print content they shouldn't.**
   - **Matched secrets.** `.githooks/pre-commit` prints the secret it found. That puts it into terminal scrollback and into the transcripts of the AI agents that run the hook.
   - **Wrong line numbers.** Both scripts print placeholder "line numbers" that are positions in a list of added lines, not lines in the file. This is a correctness fix, not injection. It's done here because item 2 rewrites the same output line.
4. **Type changes skip the placeholder scan.** A type change (`T`) is a file turned into a symlink or a gitlink.
   - Pre-commit lists staged files and diffs with `--diff-filter=ACMR`, so neither of its scans sees type changes.
   - `ci-checks.sh`'s placeholder loop uses `ACMR` too. Its secret scan already reads the whole diff.

**The realistic risk.** CI is not a security boundary against a PR author: their own YAML and test scripts run in the same Azure job as the persisted token (ADR 0005). This task is defence in depth. Every print site in the scripts fires only when a gate fails. Git's own warnings are the exception: the build review found they quote a PR's `.gitattributes` and `.gitmodules` on a passing build too (criterion 13). So the likely route is a secrets-bearing build, started by a trusted author, of content someone else wrote: an upstream starter sync, vendored files or merged contributor commits. The worst payload is `##vso[task.uploadfile]` pointed at `.git/config`, which holds the persisted extraheader token.

**Not a route.**
- **Ref names and SHAs.** `git check-ref-format` forbids `[`, `:`, space, `?`, `*`, `\`, control bytes and DEL in ref names, which rules out `##vso[`, `##[`, `::` and ANSI escapes. SHAs are hex.
- **`echo "PR build: target $target …"`, `$runner_entry` and `ci-pr-checks.sh`'s messages.** These carry only refs, SHAs and fixed paths.
- **The PR-body step.** It prints fixed section names.
- **`ci-deck-needed.sh`.** It prints fixed strings and counts.

## Users and stakeholders
- **Requester:** the owner.
- **Affected:**
  - **Adopters and fork maintainers** who sync from upstream. Their CI and hook output changes format.
  - **Anyone parsing hook output** (scripts, editor integrations). They will see `path: line N` instead of `path: N:content`.
  - **Agents that run the hooks.** They stop getting secrets echoed into their transcripts.

## Acceptance criteria
- [x] 1. **Every added line is scanned.** One hunk-aware parser, `se_added`, replaces `added_only` in both scripts. It feeds both the pass/fail decisions and the locations. Its exact rules:
  - **Starting a file.** A line starting `diff --git ` returns to header state, wherever it appears. That's safe because every content line carries a prefix.
  - **Header state.** It skips everything (`---`, `+++`, `index`, mode lines) until a line starting `@@ `.
  - **Hunk header.** `$3` must match `/^\+[0-9]+(,[0-9]+)?$/`. Then `split($3,p,","); n=substr(p[1],2)+0`. Any text after the second `@@` is ignored.
  - **In a hunk,** it looks at the first character:
    - `+`: print `n "\t" s`, where `s` is the line with its `+` removed, then `n++`;
    - space: `n++`;
    - `-`, or exactly `\ No newline at end of file`: nothing;
    - any other line starting `\`, or anything else: `exit 2` (tightened in the build review).
  - **Errors.** A non-empty line before the first `diff --git` also exits 2.
  - **Portability.** No regex intervals and no `\\` in regexes. CR stays in the content.
  - **Diff flags.** Every diff that feeds a scan uses `--no-color`. Without it, `color.ui=always` starts every line with ESC: today's `added_only` then matches nothing, which fails open.
  - **Decision greps** read content only, via `cut -f2-` of `se_added`'s output, so every decision stays exactly as it is today. Both steps are captured separately, so neither status is masked, and each is followed by `|| die` or `|| fail`:
    - `added_n=$(printf '%s\n' "$full_diff" | se_added)`;
    - `added=$(printf '%s\n' "$added_n" | cut -f2-)`.

    Git's output is always captured first (starter T-013) and never piped straight into awk.

  Confirmed by the Backend review:
  - `Binary files` lines can't appear under `--text`.
  - Mode-only changes and empty new files have no hunks.
  - With `--no-renames`, a type change appears as two `diff --git` blocks for the same path: one with `deleted file mode`, and one with `new file mode 120000` and `@@ -0,0 +1 @@`.

  Tests in `test-ci-checks.sh` and `test-pre-commit.sh`:
  - An unknown hunk line makes the parser exit 2, which fails closed.
  - `color.ui=always` in the repo config doesn't hide content.
  - A placeholder on a final line with no trailing newline gets the right line number.
  - A `++`-prefixed placeholder is blocked.
  - A `++`-prefixed AWS-key-shaped string is blocked. Both literals are assembled at runtime in the tests, so no file in the repo holds one.
  - A line whose content is `diff --git a b` and a line whose content is `@@ -1 +1 @@` are both counted correctly. This is a regression guard only, not coverage of the reset rule.
  - Hits in two hunks, and a hunk header with no `,d`, give the right line numbers.
  - A `\` line other than the no-newline marker makes the parser exit 2.
- [x] 2. **One sanitizer.** A `# BEGIN safe-echo` / `# END safe-echo` block holds `se_added`, `se_safe`, `se_lines` (line numbers of the added lines matching a pattern; patterns must not be anchored) and `se_where` (prints up to 20 `  <path>: line N` lines, then `  ...and N more`). It's byte-identical in `scripts/ci-checks.sh` and `.githooks/pre-commit`.
  - **Sanitizing.** `se_safe` takes one argument and runs `se_s=$(printf '%s' "$1" | LC_ALL=C tr -c 'A-Za-z0-9._/ -' '?') || return 1`. The trailing `-` in that set is literal in GNU, BSD and busybox `tr`.
  - **Cutting.** If `[ "${#se_s}" -gt 200 ]`, it cuts with `cut -c1-200` (with `|| return 1`) and adds `...`. `...` is ASCII, so the output stays inside the allowlist, at 203 bytes at most.
  - **Output.** It prints exactly one line and returns non-zero if any step fails. Its last command is a `printf`, so it can't rely on `set -e`.
  - **Names.** Every global in the block uses the `se_` prefix.
  - **Call sites.** Every call that decides is `sf=$(se_safe "$f") || die/fail "<fixed text>"`. In loops, that's the first line of the body, before any `|| fail` that prints the name. The hook's `secret_where` never decides, so its call is `|| continue`.

  `test-ci-wiring.sh` checks:
  - the two blocks are identical (`cmp`);
  - each marker appears exactly once in each file;
  - a drift fixture is caught.

  Tests feed `se_safe`:
  - LF, CR, ESC (`\033[2J`), `%0A`, `  ::x::` with leading spaces, and `##vso[a]b`. Each comes out as one line with no `\n`, `\r`, ESC, `%`, `:`, `#` or `[`.
  - An empty string.
  - Every byte from 1 to 255, one at a time. Each comes out as itself if it's in the set and `?` otherwise.
  - Exactly 200 bytes, which is not cut.
  - 201 bytes, which becomes 200 bytes followed by `...`.
- [x] 3. **Placeholder hits print a location, not content.**

## Plan
**Block.** `se_added` is one POSIX awk program following criterion 1's rules. `se_safe` is `tr -c`, then a length check, then `cut -c1-200` and `...` when the value is too long, then one `printf`.

**Decisions.**
- The secret decision reads `added`, captured in two steps (criterion 1), so it's content only and the existing grep runs exactly as it does today.
- The per-file placeholder grep reads `se_added`'s output for that file. `cut -f1` gives the line numbers.

**Output.** Every message with a path or subject uses a variable captured from `se_safe` at top level.

**Filters.** Every listing and diff that feeds a scan uses `ACMRT` and `--no-color`.

**Files.**
- Code: `scripts/ci-checks.sh` and `.githooks/pre-commit`.
- Tests: `scripts/test/test-ci-checks.sh`, `test-pre-commit.sh` and `test-ci-wiring.sh`.
- Docs: `.githooks/README.md` and `ADOPTING.md`. (ADR 0005 was planned and then dropped; see criterion 9.)
- Ledger: `.starter/tasks/INDEX.md` and this file.
- CI: `.github/workflows/checks.yml` and `azure-pipelines.yml` each gain the two `SH=bash` steps (criterion 12). `test-ci-wiring.sh` is updated if it pins the step list.

**Order.**
1. Write the tests, failing at first. That includes the `++` repro.
2. Add the block.
3. Wire the decisions.
4. Wire the output.
5. Change the filters.
6. Update the docs.
