# T-023 — Spec a task before its plan is reviewed (definition of ready)

## Description
The owner asked what the playbook does to help flesh out specs before agents review a task, then asked for this task.

Today a task goes straight from the template to "Plan the work — what changes, which files, what approach". The Analyst's redlines already ask for:
- testable criteria;
- a named persona;
- written-down assumptions;
- no "we'll figure out requirements during build".

The gaps:
- The template has nowhere to put users, non-functional needs, assumptions, open questions or even the plan.
- Questions for the requester have no home, and nothing says they get answered before review.
- Nothing mechanical stops a half-specified task from entering plan review.

So requirements and design get mixed in one free-form plan. Requirement gaps turn up as review findings or mid-build.

This task adds a **spec step** with a **definition of ready**:
- The task file gains four spec sections and a Plan section.
- The Analyst runs a numbered spec pass and asks the requester what only they can answer, including when they aren't present.
- A task can't enter `in-review` until every open question is answered or deferred.
- CI and the pre-commit hook enforce the mechanical part.

No new state is added. Tracing criteria to tests stays with T-009.3.

## Users and stakeholders
- **Requester:** the owner, who answers the open questions. In an adopting team, it's whoever asked for the task (a product owner, lead or customer proxy), often replying from a phone.
- **Daily users:** agents (the Analyst above all) and engineers who open and spec tasks; Round 1 reviewers, who get a ready spec instead of a free-form plan.
- **Affected:**
  - adopters syncing from upstream, whose new tasks must carry the new sections;
  - workspace-model teams, whose playbook hooks run in every sibling repo;
  - T-009.3, which later edits the same template and Analyst file.

## Acceptance criteria
Each criterion names its test. "The block" means the `task-ready` block (criterion 9). Block tests live in a new suite, `scripts/test/test-task-ready.sh` (criterion 10). It extracts the block from `scripts/ci-checks.sh` and runs it directly.

Every failing case asserts the exact findings (code, line and count) through an `expect_findings` helper, never just a non-zero exit, so a fixture that fails for the wrong reason can't pass.

**Task-file format**
- [ ] 1. **Template.** `tasks/_TEMPLATE.md` changes as follows.
  - **Frontmatter:** it gains `spec_format: 1`, with a comment pointing at `tasks/README.md#definition-of-ready`.
  - **Section order:** Description, Users and stakeholders, Acceptance criteria, Non-functional requirements, Assumptions, Open questions, Out of scope, Plan, Subtasks, Risks / dependencies, Notes, Activity log.
  - **Plan section:** guidance only, "Written once the spec is ready, before plan review"; the check never requires it.
  - **Guidance comments:** each new section has one HTML-comment line.
    - Non-functional requirements names performance, security and privacy, accessibility, reliability, and data and compliance (name any regulation), and adds "One line is fine, e.g. `n/a — docs-only change.`".
    - Users and stakeholders, Assumptions and Open questions say "`None.` is fine".
    - The Acceptance criteria comment says edge and error cases are criteria of their own.
    - The Open questions comment includes one valid example each of an open, an answered and a deferred line. The check ignores comments.
  - **Activity log:** the example goes from proposed to in-review "once ready".

  `test-task-ledgers.sh` checks:
  - the section order;
  - that the Non-functional guidance contains each category;
  - the wording of the activity-log example.

  The block is tested on a copy of the template. With `state: in-review` it must fail with exactly these findings:
  - `SPEC_EMPTY_SECTION` for Users and stakeholders, Non-functional requirements, Assumptions, Open questions and Out of scope;
  - `SPEC_PLACEHOLDER_AC`.

  With `state: proposed` it must pass.
- [ ] 2. **Frontmatter fails closed.**
  - Line 1 must be exactly `---`, so a BOM fails, and a closing `---` must exist.
  - The `state:` key is matched case-insensitively, with leading whitespace allowed. Its value is taken after dropping `[ \t]+#.*$` and trimming. The key must appear exactly once, and its value must be one of `proposed`, `in-review`, `in-progress`, `completed`, `blocked`, `cancelled`, exactly and in lowercase.
  - The `spec_format:` key is handled the same way and appears at most once.
  - Any line ending in CR fails at the first such line. Parsing continues with CR stripped, so other findings still show.

  Every one of these fails with `SPEC_FRONTMATTER <file>: line <n>`, whatever the state. Block tests cover each one:

  | Input | Result |
  |---|---|
  | BOM | fails |
  | CRLF | fails |
  | no opening `---` | fails |
  | unclosed `---` | fails |
  | `State: In-Review` | fails |
  | `state: inreview` | fails |
  | two `state:` lines | fails |
  | no `state:` line | fails |
  | two `spec_format:` lines | fails |
  | `state: in-review  # comment` | passes |
  | CR on body line 40 only | fails `SPEC_FRONTMATTER` at line 40 |
  | CRLF plus an open question | reports both findings |
- [ ] 3. **Open questions (rule 2).** This applies when the state is `in-review`, `in-progress` or `completed`, in every `## Open questions` section.
  - **Checkbox items.** An item is a line matching `^[ \t]*([-*+]|[0-9]+[.)])[ \t]+\[[^]]*\]`, after every comment span on the line is removed. Items inside blockquotes aren't counted.
  - **Valid boxes.** `[ ]` is open and fails `SPEC_OPEN_QUESTION`. `[x]` and `[X]` are checked. Any other box (`[]`, `[-]`, `[ x]`) also fails `SPEC_OPEN_QUESTION`.
  - **Checked items** need one of two things after the box:
    - **An answer.** `Answer (` followed by `<date>, <who>, <source>` and then `): `, which must be followed by at least one word on the same line.
      - The date has the shape `NNNN-NN-NN`.
      - The source is the part after the last `, `. It must be `in session`, or `http://` / `https://` followed by characters that aren't spaces, commas or `)`.
      - `<who>` is everything in between. It may contain commas, but not `(` or `)`.
      - Indented lines below the item continue the answer.
    - **A deferral.** `Deferred to T-<n>[.<n>…]: ` followed by at least one non-blank character.

    A checked item with neither fails `SPEC_UNANSWERED`.
  - **Ignored lines.** Text inside HTML comments (one line or several) or inside fences is ignored. A fence opens on a line starting, after whitespace, with three or more backticks or tildes. It closes on a fence of the same character that is at least as long.
  - **States not checked.** `proposed`, `blocked` and `cancelled`.

  Block tests cover:
  - each bullet style, `[X]`, and each invalid box;
  - `<!-- c --> - [ ] q`, which counts as an open item;
  - an answer that wraps onto an indented line (passes), and an `Answer (` header that sits only on the next line (fails);
  - a missing source, a URL source, and a `<who>` that contains a comma (passes);
  - `Answer (2026-11-11, in session, Jane): x`, where the source is before the name (fails);
  - `Answer (…): ` with nothing after it, a `2026-1-11` date, and parentheses in `<who>` (each fails);
  - `Deferred to T-: x` (fails) and `Deferred to T-24.1.2: why` (passes);
  - items inside a comment, a fence or a blockquote;
  - fences that don't close: a ```` ```` ```` fence followed by a ```` ``` ```` line, and a ```` ``` ```` fence followed by `~~~`. Both stay open and fail `SPEC_UNCLOSED`;
  - a `[ ]` under a `### Details` heading inside Open questions (fails, because a level-3 heading doesn't end the section);
  - a second `## Open questions` section;
  - an open question in `completed` (fails), and in `blocked` and `cancelled` (both pass);
  - `in-review` in one commit with a question added in the next (fails at head);
  - `blocked` back to `in-review` with a question still open (fails);
  - a question added while `in-progress` (fails, with a Fix line pointing at `blocked`).
- [ ] 4. **Required sections (rule 3).** These apply to a task with `spec_format: 1` whose state is `in-review` or later.

  | Finding | Fails with |
  |---|---|
  | One of the six required sections is missing (Users and stakeholders, Acceptance criteria, Non-functional requirements, Assumptions, Open questions, Out of scope) | `SPEC_MISSING_SECTION <name>` |
  | A required section has no content line. A content line is any non-blank line outside comments and fences that isn't only `…` or `- …`. So a bare `n/a` or `None.` counts. | `SPEC_EMPTY_SECTION <name>` |
  | The Acceptance criteria section has no checkbox item, or has one whose text right after the box starts with `<given>` | `SPEC_PLACEHOLDER_AC` |
  | A required section appears twice | `SPEC_DUPLICATE_SECTION` |
  | A `spec_format:` value other than `1`, checked in every state | `SPEC_VERSION_UNKNOWN` |

  **Headings.**
  - An exact heading is `^## <Name>$`.
  - A loose match ignores case, collapses whitespace, and allows any `#` level, up to 3 leading spaces, trailing `#`s, and a name followed by end of line, `(` or `:`.
  - A heading that only matches loosely fails `SPEC_HEADING`, with a Fix line giving the exact text. Examples: `## Open Questions`, `### Open questions`, `## Out of scope (follow-ups)`.
  - In a file without the marker, only the Open questions near-miss is checked, so rule 2 can't be dodged.
  - A section ends at the next level-1 or level-2 heading.
  - Fenced lines never start a section.

  Block tests:
  - each of the six required sections missing, and a duplicate section;
  - `spec_format: 2` under `proposed` (fails);
  - a section holding only `…` (empty), only `n/a` (content), only a fence (empty), or only a comment (empty);
  - an AC section with prose but no checkbox, and a checkbox item starting with `<given>`;
  - each loose heading form: case, `###`, trailing `#`s, `(`, `:`, and 3 leading spaces all match; 4 leading spaces doesn't;
  - a legacy file with `## Out of scope (x)` (passes), and one with `## Open Questions` (fails).
- [ ] 5. **Unclosed regions.** A comment or fence still open at end of file fails `SPEC_UNCLOSED <file>: line <opening line>`, whatever the state. That way it can't hide what follows. A block test covers each kind.
- [ ] 6. **Marker rules (rules 4 and 5).**
  - **Missing marker.** A file added under the project's `tasks/` without `spec_format:` fails `SPEC_MARKER_MISSING`, whatever its state. Three cases are exempt:
    - `.starter/tasks/`, which is upstream's ledger; forks get older upstream files as additions when they sync.
    - CI root mode (an empty-tree base).
    - Pre-commit with an unborn HEAD. This is treated exactly like root mode, so a new repo's first commit of the seeds isn't blocked.
  - **Removed marker.** A modified (`M` or `T`) file that had `spec_format:` at its base (`$from:$path` in CI, `HEAD:$path` in pre-commit) and no longer has it fails `SPEC_MARKER_REMOVED`. The base copy is read only for `M` and `T` entries; a failed read fails closed. In root mode or with an unborn HEAD the comparison doesn't run. The base's marker is found with the same awk program.

  Existing tasks without the marker (the seeds and the starter's history) are checked only for `SPEC_FRONTMATTER`, `SPEC_UNCLOSED`, `SPEC_BAD_NAME`, `SPEC_NOT_A_FILE`, `SPEC_OPEN_QUESTION`, `SPEC_UNANSWERED`, and `SPEC_HEADING` on an Open questions near-miss.

  `test-ci-checks.sh` and `test-pre-commit.sh` cover:
  - an added `tasks/` file without the marker: fails;
  - an added `.starter/tasks/` file without the marker: passes;
  - CI root mode: passes;
  - an unborn-HEAD first commit of seed-like files: passes;
  - removing the marker: fails;
  - an unreadable base: fails closed;
  - a modified legacy file: passes;
  - a legacy `tasks/` file renamed to another valid ID: fails `SPEC_MARKER_MISSING`. This is deliberate, because IDs are never renumbered, so a move is a new task.
- [ ] 7. **Which files, and how they're read.**
  - **Listing.** One `git diff --name-status --no-renames --diff-filter=ACMRT` call gives each path's status. CI root mode uses the empty-tree diff, and pre-commit uses `--cached`. Pre-commit's existing early-exit list moves from `ACMR` to `ACMRT`, so a commit whose only change is a type change still reaches the check. Paths are relative to the repo root; `x/tasks/…` is not a task file.
  - **Bad names.** A path whose prefix matches `^"?(\.starter/)?tasks/T-` case-insensitively but that doesn't match `^(\.starter/)?tasks/T-[0-9]+(\.[0-9]+)*\.md$` exactly fails `SPEC_BAD_NAME`. That catches `T-024a.md`, `Tasks/T-1.md`, `tasks/t-1.md`, a git-quoted name, and anything under `tasks/T-1/`.
  - **Mode.**
    - CI checks it with `git ls-tree "$head"`.
    - Pre-commit uses `git --literal-pathspecs ls-files --stage`, which reads the index and so honours `GIT_INDEX_FILE` (as with `git commit <path>`).
    - Anything other than mode 100644 or 100755 at stage 0 fails `SPEC_NOT_A_FILE`.
  - **Reading.** `git cat-file blob` at `$head:$path` in CI, or `:0:$path` in pre-commit, captured into a variable before the block reads it. Any git failure fails closed with the existing "could not all run" message.
  - **Workspace model.** In a sibling repo, the playbook's hooks check that repo's `tasks/`. The playbook's own `tasks/` is checked by its own CI.

  Tests cover:
  - each bad-name form;
  - a symlinked task file in CI, and one staged in pre-commit;
  - a type-change-only commit;
  - a staged version that differs from the working tree;
  - `git commit <path>`;
  - a subtask ID like `T-1.2.3`.
- [ ] 8. **Output, from the user's side.** A file with findings prints a summary line first: `Task <file> is not ready (<n> problems):`. Each finding then prints:
  - `<CODE> <file>: line <n>` (or the section name), with a plain-language reason in parentheses;
  - an indented `Fix:` that says exactly what to type or change. Open questions get the answer line's shape, "Already answered? Change `[ ]` to `[x]`", "Deferred to T-<n>: why", and which state to set while waiting (see criterion 12). A heading finding gets the exact heading. `SPEC_UNANSWERED` names the common slips: the header on the next line, a missing source, a date not in `YYYY-MM-DD` form, or parentheses in the name (write `Jane, PM`, not `Jane (PM)`).

  The output ends with `See tasks/README.md#definition-of-ready`. The block writes to stdout, and the caller prints the captured output to stderr.

  Only fixed strings, line numbers and the path are printed. No content from the file is echoed, because Azure DevOps acts on `##vso[` anywhere in a log line. An echoed path has every character outside `[A-Za-z0-9._/-]` replaced with `?`.

  When every file passes, the caller prints `task-ready: <n> task file(s) checked`, so a no-op that checked nothing still shows up in the log.

  Block tests check:
  - every code has a Fix line. The list of codes is built from the block's own source, so a new code can't skip the test;
  - the summary line and the README link are printed;
  - a canary string written into every line of a fixture never appears in the output, for any code;
  - a bad name containing `##vso[` is printed sanitized.

**The check itself**
- [ ] 9. **One block, two places.** The check is a single block between `# BEGIN task-ready` and `# END task-ready`. It is byte-identical in `scripts/ci-checks.sh` (check 5; the script stays self-contained) and `.githooks/pre-commit` (check 6).
  - **Isolation.** The block reads only its arguments and stdin. It defines only `tr_`-prefixed names, never calls `die`, `err` or `fail`, and checks every status itself, because it runs inside `||` where `set -e` does nothing.
  - **Exit codes.** It returns 0 when ready, 1 for findings and 2 for an internal error.
  - **awk output.** awk prints `CODE<TAB>detail` lines and always ends with one `MARKER<TAB>0|1` line. The block treats it as an internal error if awk prints any line that isn't a known code or MARKER, if the MARKER line is missing, or if awk exits anything other than 0. busybox awk exits 1 on its own errors, so exit 1 never counts as a result. The path never enters the awk program, and `-v` isn't used.
  - **Caller pattern.**
    ```
    tr_rc=0; tr_out=$(printf '%s\n' "$tr_blob" | tr_check …) || tr_rc=$?
    ```
    followed by a `case` on 0, 1 or 2. Callers loop with IFS set to newline and `set -f`, as check 1 does. They never use `| while read`.
  - **Portability.** POSIX awk only: no `{n,m}`, `\s`, `IGNORECASE`, `gensub`, `length(array)` or bracket character classes. The block sets `LC_ALL=C` itself, because the hook runs in the user's locale.
  - **Placement.** Check 5 runs after check 4 and before the final summary, so a `die` on exit 2 can't hide findings from checks 1–4. CI reads modes with `git --literal-pathspecs ls-tree --full-tree "$head" -- "$p"`, so the result doesn't depend on the working directory.

  Internal-error tests in `test-task-ready.sh` use awk shims that do each of the following, and every one must return 2:
  - exit 2;
  - exit 1 with valid output (the busybox case);
  - print an unknown code;
  - leave out the `MARKER` line;
  - print `MARKER` twice.

  `test-ci-checks.sh` and `test-pre-commit.sh` each put a broken awk on `PATH` and expect "could not all run".

  Static greps on the extracted block find no calls to `die`, `err` or `fail`, no `-v`, no function without the `tr_` prefix, and none of the banned constructs (`[[:`, `\s`, `IGNORECASE`, `gensub`, `{[0-9]`). The greps are needed because mawk 1.3.4 accepts bracket classes, so no runner awk would catch them.

  `test-ci-wiring.sh` extracts both blocks and compares them with `cmp`. It fails if they differ, or if either marker is missing or appears twice, with a fixture for each case. A `test-ci-pr-checks.sh` case shows that a PR deleting the block from its own `ci-checks.sh` is still checked, because the target branch's copy runs.
- [ ] 10. **Test coverage.**
  - **New suite.** `scripts/test/test-task-ready.sh` is a new step in the shell-scripts job of both `.github/workflows/checks.yml` and `azure-pipelines.yml`. `test-ci-wiring.sh` asserts it is present in both.
  - **awks.** Each awk is put on `PATH` through a shim directory, not an environment variable. The suite prints `awks: awk=ran mawk=ran|skipped gawk=… busybox=…`.
    - In CI (detected by `GITHUB_ACTIONS` or `TF_BUILD`, as `test-deck.sh` does), a missing `mawk`, Ubuntu's default awk, is a FAIL.
    - A missing `gawk` or `busybox` prints a visible SKIP line. Neither is listed in the Ubuntu 24.04 runner image.
    - BWK awk runs on macOS. The `awks:` line is for information only; the mawk FAIL is what enforces coverage.
  - **Shells.** The suites run their cases under each available shell (`dash`, `bash --posix`, `busybox sh`), in the same loop as the awks, so no extra CI steps are needed.
  - **Isolation and locale.**
    - An isolation case sets `IFS`, `f`, `p`, `rc`, `out` and the `set -f` state before calling the block, then asserts none of them changed.
    - One case runs the block under `env -i PATH=<shim dir>:/usr/bin:/bin`.
    - One case runs under a UTF-8 locale, where one is available.
  - **Determinism.** Every case uses temp repos, an isolated git config and no network, as the existing suites do. `test-task-ready.sh`, `test-ci-checks.sh` and `test-pre-commit.sh` pass under sh and dash and are shellcheck-clean.
  - **Whole ledger.** `test-task-ledgers.sh` runs `tr_check` over every `tasks/T-*.md` and `.starter/tasks/T-*.md` in the working tree, the way check 5 would for an added file. It expects every file to pass. It also asserts two things, so a glob that matches nothing can't pass:
    - the files checked are exactly the task IDs in the `| [T-…](…)` rows of `tasks/INDEX.md` and `.starter/tasks/INDEX.md`, matched both ways (today 19 + 26);
    - `T-023` reported `MARKER 1`.

    This is how this file's own readiness is proven (criterion 15). This PR is judged by the old gate on `main`, so the trusted gate's first real enforcement is the push to `main` (see Risks).
  - **Rollback path.** `test-ci-checks.sh` has a case for a range that deletes `.starter/tasks/T-x.md` and modifies `tasks/_TEMPLATE.md` and an INDEX. It passes, so a revert PR shaped that way can't be blocked by the check.
  - **Doc examples.** The template's and README's example lines are uncommented and run through the block. They must give exactly one `SPEC_OPEN_QUESTION`, from the example open line, so the examples in the docs can't rot.

## Non-functional requirements
- **Performance:** per changed task file, one `ls-tree` or `ls-files`, one or two `cat-file` calls and one awk run. That adds well under a second to a CI run or a commit.
- **Security and privacy:**
  - File content reaches awk only as data on stdin, and nothing from it is echoed (criterion 8).
  - Names are gated by an anchored pattern before any git call, and reads are literal blob reads with no textconv.
  - A PR is judged by the target branch's check (starter T-014).
  - No new secrets or permissions.
- **Accessibility:** n/a — there's no UI. Messages are plain text, start with a summary, and each one carries a `Fix:` line.
- **Reliability:**

## Plan
**Approach.** The block defines three shell functions, all used by both callers. The name rules and the marker rules live inside the block, where the `cmp` drift test covers them:
- `tr_name <path>`: returns 0 for a task file, 1 for a bad name, 3 for a file that isn't a task file.
- `tr_marker`: reads stdin; returns 0 if the marker is present, 1 if not, 2 on error.
- `tr_check <path> <marker_required:0|1> <base_marker:0|1|->`: reads a task file on stdin and runs one POSIX awk program over it. The caller sets `marker_required=1` only for an `A` entry under `tasks/`, outside root mode and not on an unborn HEAD. The awk program:
- strips CR, then parses the frontmatter;
- walks the lines, tracking comments, fences and sections;
- prints `CODE<TAB>line-or-section` findings, then a final `MARKER<TAB>0|1` line.

The shell then:
- validates the awk output;
- applies the marker rules;
- adds the path (sanitized), the reason, the `Fix:` lines and the summary;
- returns 0, 1 or 2.

**Callers.** Both wrap the same `# BEGIN task-ready` block.
- **`scripts/ci-checks.sh`, check 5.**
  1. `git diff --name-status --no-renames --diff-filter=ACMRT "$from" "$head"` (root mode uses the empty-tree diff).
  2. For each line, gate the name, then check the mode with `ls-tree "$head"`.
  3. Read `cat-file blob "$head:$p"` into a variable.
  4. For `M` or `T` entries, read `$from:$p` and find its marker.
  5. Call the block. Exit 2 calls `die`; exit 1 calls `err`.
- **`.githooks/pre-commit`, check 6.** The same steps over `git diff --cached`, with these differences:
  - the mode comes from `ls-files --stage`;
  - the file is read from `:0:$p`;
  - the base is `HEAD:$p` (skipped when HEAD is unborn);
  - the early-exit filter becomes `ACMRT`.

This follows T-022's identical-block precedent and its drift test.

**Files.**
- **Check:** `scripts/ci-checks.sh`, `.githooks/pre-commit`.
- **Tests:**
  - new `scripts/test/test-task-ready.sh`;
  - `test-ci-checks.sh`, `test-pre-commit.sh`, `test-ci-wiring.sh`, `test-ci-pr-checks.sh`, `test-task-ledgers.sh`, `test-deck.sh`.
- **CI:** one new step each in `.github/workflows/checks.yml` and `azure-pipelines.yml`, for the new suite.
- **Docs:** `tasks/_TEMPLATE.md`, `tasks/README.md`, `AGENTS.md`, `.claude/agents/analyst.md`, `.claude/agents/review-coordinator.md`, `README.md`, `.githooks/README.md`, `ADOPTING.md`.
- **Deck:** `scripts/build_deck.py` and the rebuilt deck.
- **Ledger:** `.starter/tasks/INDEX.md` and this file.

## Seven lenses (plan)
1. **CEO.** The pitch is "the playbook now makes agents ask before they build." That's a clean story for a public starter. One risk to its reputation: a gate that fails on reasonable files. The fail-closed rules are strict, but every finding names its fix, and the whole-ledger test proves today's files pass.
2. **Purchasing.** No new dependencies, vendors or permissions: POSIX sh and awk, which the runner and macOS already have. CI cost is a few seconds per run.
3. **Product/PM.** It's buildable in one PR, but a big one: three review rounds turned it into 15 criteria and a test matrix. It's the right next thing because T-009.3 edits the same files and is easier to build on top of a stable template. The criteria are pinned, which limits scope creep. The reviews' findings about existing code are split into a separate task.
4. **Adopter.** This is the main tension.
   - **For:** the spec pass and question bank give the Analyst and engineers a real procedure, and requesters answer in plain comments without editing files.
   - **Against:** four new sections are homework on a one-line task. The plan mitigates this with "`None.` is fine" and "One line is fine" hints.
   - **The landmine:** forks that already write `## Open questions` sections. The sync note warns about it.
5. **Builder.** Two identical blocks in two files is a maintenance cost. The `cmp` drift test, the `tr_` isolation, the static greps and the four-awk shims make it safe to change. A maintainer would be proud of the tests, less so of a several-hundred-line awk program. The plan keeps the awk to one pass, with codes defined in one place.
6. **Investor.** It deepens the moat: few agent playbooks have a mechanical definition of ready. It also pairs with T-009.3 for a "spec → test → evidence" story. No unit-economics concern.
7. **Marketing/Sales.** It demos well. Open a task with an unanswered question, and the commit is refused with a plain message that says what to type. Predictable objection: "more process". Answer: the check only reads what the template asks for, and a small task writes about four lines more.

**Conflicts.** Adopter (homework) vs. Builder and CEO (strictness). This was resolved in Round 2: the sections stay required, but `None.` and `n/a — <reason>` are valid content, and the template says so. No conflict is left unresolved.
