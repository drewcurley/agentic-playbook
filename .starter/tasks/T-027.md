# T-027 — Make ci-pr-checks.sh discard git's stderr

## Description
Starter T-024 made every git call in `scripts/ci-checks.sh` and `.githooks/pre-commit` discard git's stderr, enforced by `check_git_quiet` in `scripts/test/test-ci-wiring.sh`. `scripts/ci-pr-checks.sh` wasn't covered.

- **Current calls are quiet.** Its git calls today are `rev-parse --verify`, `ls-tree --full-tree` and `cat-file blob`. On 2026-11-14 none of them printed a warning against a hostile `.gitattributes` or `.gitmodules`. So this is defence in depth.
- **Why do it anyway.** A future call there, such as a diff, would put a PR's bytes into the log.

The task is to give every git call in `ci-pr-checks.sh`, and in the CI files' `procedure` steps, the same `2>/dev/null`, and extend `check_git_quiet` and its fixtures to them. Two additions came out of plan review: each CI call gets a fixed failure message, because a silent `set -e` exit would leave a red build with no reason; and `check_git_quiet` is tightened for every script, because it missed forms such as `if git …` and `$( git …)`.

## Acceptance criteria
- [ ] 1. **Every git call in `scripts/ci-pr-checks.sh` discards git's stderr.** The `rev-parse` and `ls-tree` captures become `$(git … 2>/dev/null)`. The two `cat-file blob … > file` redirects gain `2>/dev/null`. A failing call still fails closed with the existing `CI-PR-CHECK FAIL` message.
- [ ] 2. **So does every git call in the `procedure` job's script steps.** That covers Azure's `head=` line and its pr-mode and trusted-gate blocks, and GitHub's `target_sha=` line and its trusted-gate block. Each `rev-parse`, `ls-tree` and `cat-file` gains `2>/dev/null` and, since a silent `set -e` exit would leave a red build with no reason, a fixed message: `|| { echo "${err}<what failed>. Failing closed."; exit 1; }`, where `err` is set to `##[error]` on Azure and `::error::` on GitHub before the markers, the way `$warn` is, so the trusted-gate block stays identical in both files. Exactly one call keeps its stderr: Azure's `git fetch -q --no-recurse-submodules origin "$target"`. It fetches the target branch, not the PR; with recursion off it reads no `.gitmodules`; and its remaining messages come from the remote and the target name, which can't contain `[`. This task adds `--no-recurse-submodules`.
- [ ] 3. **Wiring checks enforce it.** In `scripts/test/test-ci-wiring.sh`:
  - `check_git_quiet` is tightened for every list: it also counts `$( git` with a space, and treats a git call after `!`, `if`, `then`, `elif`, `else`, `while`, `until` or `do` as bare.
  - A second list, `quiet_scripts`, holds `scripts/ci-pr-checks.sh` and starter T-028's `.githooks/commit-msg`. There, a bare git call is accepted only when its line has exactly one, a stdout redirect matching `[^0-9&>]>[ \t]*"?[$]`, and `2>/dev/null`. The T-024 scripts in `se_scripts` stay captures-only.
  - `check_ci_git_quiet` applies the capture rule, and the fixed-message rule, to every git call in both CI files' `procedure` script steps, allowing only the fetch line above, matched exactly, including `--no-recurse-submodules`.
  - A fixture fails each rule and each new form. Today's four scripts and two CI files pass.
- [ ] 4. **A noisy git leaves no bytes in the output.** `test-ci-pr-checks.sh`'s git stub gains a `STUB_NOISE` mode: every call prints `##vso[task.logissue]t027` and an ESC byte to stderr, then runs the real git. With it, `run_pr` and the CI blocks' runs show neither in their output, on either stream. Fixture setup doesn't run under the stub. This fails before the change, and on dropping `2>/dev/null` from any one call.
- [ ] 5. **Failures still say why.** For each CI-block call, a stubbed failure shows its fixed message, matched without the platform prefix, not only a non-zero exit.
- [ ] 6. **Docs.** The `ADOPTING.md` T-024 note's "every git call" bullet names `ci-pr-checks.sh`, `commit-msg` and the CI `procedure` steps.
- [ ] 7. **No regression.** Every existing case in every suite passes under sh, dash and bash, and shellcheck is clean.

## Out of scope
- The checkout step (starter T-025) and the `commit-msg` hook (starter T-028).

## Plan
**Code.** Add `2>/dev/null` inside each `$(git …)` in `scripts/ci-pr-checks.sh` and after each `cat-file` redirect. In both CI files, do the same for every git call in the `procedure` script steps except the fetch, and give each a fixed failure message.

**Check.** Tighten `check_git_quiet`, add `quiet_scripts` with the redirect form, and add `check_ci_git_quiet` (criterion 3).

**Files.**
- Code: `scripts/ci-pr-checks.sh`, `.github/workflows/checks.yml`, `azure-pipelines.yml`.
- Tests: `scripts/test/test-ci-pr-checks.sh`, `scripts/test/test-ci-wiring.sh`.
- Docs: `ADOPTING.md` (the T-024 note's "every git call" bullet names the newly covered files).
- Ledger: this file, `.starter/tasks/INDEX.md`.

## Risks / dependencies
- `ci-pr-checks.sh` runs on the target branch's copy, so the change protects PRs only after it lands on main.
- Its two `git cat-file blob … > file` calls are redirects, not `$( )` captures. `check_git_quiet` flags any git call outside a capture, so either the check or those calls must change.
- Starter T-028 adds `.githooks/commit-msg` to `quiet_scripts`, so the two are built in one PR.
