# T-025 — Keep the CI checkout step's git warnings out of the log

## Description
Starter T-024 made `scripts/ci-checks.sh` and `.githooks/pre-commit` discard git's own stderr, because git's warnings quote a PR's `.gitattributes` and `.gitmodules`. The CI checkout step runs git before either script: `actions/checkout` in `.github/workflows/checks.yml`, and `checkout: self` in `azure-pipelines.yml`.

- **What leaks.** An invalid attribute name in a PR's `.gitattributes`, such as `##vso[task.logissue`, is printed by `git clone` and `git status` as "`<name>` is not a valid attribute name". T-024's build review confirmed this on 2026-11-14.
- **Why it matters.** Azure DevOps acts on `##vso[` anywhere in a log line. GitHub Actions acts on `::cmd::` at the start of one, and this warning line starts with the attribute name. A name can't hold a space or `=`, but it can hold ESC.
- **Who's affected.** Teams that run either CI system on PRs from contributors.
- **Why the procedure job matters most.** After checkout, the `procedure checks` job runs only the target branch's code, apart from the bootstrap path when the target has no `ci-pr-checks.sh`. So the PR's bytes reach that job's log only through git's own output: from checkout, and from the step's own `git fetch` (azure-pipelines.yml:192). ADR 0005 says CI is a procedural gate, not a security boundary, and relies on code-owner review of the CI files; this task keeps a PR from steering that gate without touching them.
- **The Azure route.** Azure logging commands that take no properties need no space, and their value runs to the end of the line. With `##vso[task.prependpath]x` as an attribute name, git's suffix ` is not a valid attribute name: .gitattributes:1` is split on `:` into separate `PATH` entries, ending in a relative `1`. A PR that ships `1/bash` would then run as the shell of every later step, the gate included. Whether Azure acts on commands in checkout's output is unverified, so criterion 1 checks it first. `uploadfile`, `setsecret` and `complete` are made harmless by the same suffix, and `addbuildtag` is cosmetic.
- **The GitHub route** is cosmetic: `::add-path::` and `::set-env::` are disabled, so the warning, which starts a line, reaches only `::notice::`, `::error::`, `::add-mask::` and `::stop-commands::`. Git's `warning()` lines, such as the `.gitmodules` one, start with `warning: ` and turn ESC into `?`, so they can't start a command there.
- **Two inputs, two settings.** `attr.tree` makes git read attributes from a given tree instead of the work tree; a value that doesn't resolve reads as an empty tree. On 2026-11-14, set to the empty-tree ID through `GIT_CONFIG_COUNT`, it silenced `git clone` and `git status` of a hostile repo, which printed the name with its ESC byte without it. It does nothing for `.gitmodules`: a hostile submodule name still prints from `git fetch`, `git status` and `git submodule`. Turning recursion off (`fetch.recurseSubmodules=false`, `submodule.recurse=false`, `--no-recurse-submodules`) quiets `fetch` and `checkout`, but `git status` and `git submodule` read `.gitmodules` whatever the settings.

The task is to find out what each platform's checkout step lets us control, then either close the route or record it as an accepted residual in an ADR. Plan review added two items: a new ADR for the routes that stay open (the `.gitmodules` route through `git status`, and commit subjects on Azure branch builds), and CODEOWNERS ownership of every `.gitattributes` and `.gitmodules`, not only the root `.gitattributes`.

## Acceptance criteria
- [ ] 1. **Reproduce on real CI first, safely.** A canary PR from a branch of this repo (not a fork), opened as a draft titled `DO NOT MERGE: T-025 canary`, with auto-merge never enabled. It adds:
  - a `.gitattributes` with the attribute names `##vso[build.addbuildtag]t025-canary`, `##vso[task.prependpath]t025canary-nonexistent` and `::notice::t025-canary`;
  - a `.gitmodules` entry named `##vso[build.addbuildtag]t025-gitmodules` with `path = -x`, and a gitlink at `-x`, so a status-type command would print it;
  - a canary-only step in each CI file, after checkout, that prints `$PATH`.

  It adds no executables. The task records, with run links: whether checkout and the step's `git fetch` printed each name, whether Azure added a tag, changed `PATH` or warned "Unable to process command", whether either checkout runs `git status` or `git submodule`, and whether GitHub showed the notice. The PR is then closed unmerged and its branch deleted, in the same session.
- [ ] 2. **The procedure job reads no PR attributes and recurses into no submodules.** In both CI files, the `procedure` job sets `GIT_CONFIG_COUNT: 3` with `attr.tree` = `4b825dc642cb6eb9a060e54bf8d69288fbee4904` (the empty tree), `fetch.recurseSubmodules` = `false` and `submodule.recurse` = `false`. "Job level" means `env:` beside `steps:` under `procedure:` on GitHub, and `variables:` under `- job: procedure` on Azure; pipeline-wide settings don't count. Azure's `git fetch` keeps the `--no-recurse-submodules` flag that starter T-027 adds; this task's wiring check asserts it. A second canary run, from a branch based on the fix, shows none of criterion 1's effects.
- [ ] 3. **Fallback, only if criterion 2's run shows Azure's checkout ignores the job's variables.** The Azure `procedure` job switches to `checkout: none`. Its first script step fetches and checks out the PR with the same settings, `2>/dev/null` and `target: { commands: restricted, settableVariables: none }`, after the docs confirm that restricted mode refuses `prependpath`. The canary run is repeated and recorded. The scripted fetch works anonymously only on public repos, so a private fork's setup goes to criterion 7. This changes no file beyond those listed in the Plan.
- [ ] 4. **The gate step checks that the settings arrived.** Before any other git call, each procedure script step runs a probe in its own marked block (`BEGIN attr-probe`), on PR and branch builds alike: in a temp repo with a work-tree `.gitattributes` setting `t025probe` on `probe`, `git check-attr t025probe probe` must print `unspecified`. It fails closed with a plain message otherwise. This proves on every run that the job's variables reached the step and that this git honours `attr.tree`; a version check can't do both. As defence in depth only, each procedure script step sets `PATH=/usr/sbin:/usr/bin:/sbin:/bin` on its first line after an optional `set -e`, outside every marked block. It can't protect the shell that runs the step, which the agent finds on `PATH` before the first line runs; criterion 2 is the real control.
- [ ] 5. **Tests.**
  - `scripts/test/test-ci-wiring.sh` checks that both files set the three variables at job level, that Azure's fetch has `--no-recurse-submodules`, that the `PATH` pin is the first line of each procedure script step after an optional `set -e` and comes before `BEGIN attr-probe`, `BEGIN pr-mode` and `BEGIN trusted-gate`, that no git call comes before `BEGIN attr-probe`, that `.github/CODEOWNERS` owns `.gitattributes` and `.gitmodules` at any depth, and, under criterion 3 only, that the scripted fetch has `2>/dev/null` and the `target:` settings. A fixture fails each rule.
  - A behaviour test reads the three values from each CI file through the same parser, then runs `git clone`, `git fetch` and `git checkout` of a hostile fixture repo (the criterion 1 names, ESC bytes, and a gitlink) with them: no canary and no ESC on either stream. It also runs `git status` and asserts that it still prints the `.gitmodules` name, which pins the residual criterion 7 records; its failure message says that if git stops printing it, the ADR needs updating. Its precondition shows that the same commands without the values print the canary, and it fails, never skips, if they don't.
  - The probe block runs under `test-ci-pr-checks.sh` with the settings (passes) and without them (fails closed with its message). The existing tests that run the pr-mode and trusted-gate blocks set the three values, read through the same parser.
- [ ] 6. **Docs.** The `ADOPTING.md` sync note says the procedure job now ignores in-tree `.gitattributes` and doesn't recurse into submodules, so LFS and `eol` filters don't apply there (its scan already diffs with `--text`). A comment in each CI file explains the variables. `.github/CODEOWNERS` owns every `.gitattributes` and `.gitmodules`, not only the root `.gitattributes`.
- [ ] 7. **A new ADR records what stays open.** At least two routes. The `.gitmodules` route: any Azure checkout or later procedure step that runs `git status` or `git submodule` still prints a hostile submodule name, and criterion 1 says whether checkout does. The commit-subject route: on Azure branch builds, checkout prints `HEAD is now at <sha> <subject>`, and a squash merge's subject is usually the PR title. PR builds check out the generated merge commit, so they aren't affected. The ADR also covers any route criteria 1 to 3 couldn't close, and runs the full review cycle with a `unanimous-consensus:` line.
- [ ] 8. **No regression.** Every suite passes under sh, dash and bash, shellcheck is clean, and all four required checks pass on the build PR.

## Out of scope
- Git calls in the repo's own scripts (done in starter T-024; `ci-pr-checks.sh` and `commit-msg` are starter T-027 and T-028).
- The stderr of the procedure steps' other git calls (`rev-parse`, `ls-tree`, `cat-file`): starter T-027 covers it. Starter T-027 also adds `--no-recurse-submodules` to Azure's fetch; this task's wiring check asserts it.
- The `scripts` and `deck` jobs. They run the PR's own code by design, so a PR can already print anything there, and neither decides the procedure gate.

## Plan
**Order.** The build starts after starter T-023 and then starter T-027 + T-028 have merged, and rebases onto them. T-027 also edits both CI files' procedure steps, `test-ci-wiring.sh` and `test-ci-pr-checks.sh`.
1. Push the canary branch and open the draft canary PR (criterion 1). Record the runs.
2. Write the wiring, behaviour and probe tests, failing at first.
3. Add the job variables, the probe and the `PATH` pin, and the CODEOWNERS entries.
4. Re-run the canary from a branch based on the fix (criterion 2). Use the fallback only if needed (criterion 3). Close the canary PR and delete its branches.
5. Write the ADR and update the docs and CODEOWNERS. Run every suite under sh, dash and bash, then shellcheck.

**Files.**
- CI: `.github/workflows/checks.yml`, `azure-pipelines.yml`.
- Tests: `scripts/test/test-ci-wiring.sh`, `scripts/test/test-ci-pr-checks.sh`.
- Docs: `ADOPTING.md`, `.github/CODEOWNERS`, a new ADR in `.starter/docs/decisions/`.
- Ledger: this file, `.starter/tasks/INDEX.md`.

**Why the variables, not `git -c`.** `actions/checkout` and Azure's `checkout: self` run git themselves, so only the environment reaches them. `actions/checkout` copies its process environment into git's, and the canary shows whether Azure's does.

## Risks / dependencies
- The checkout step belongs to the CI platform, so a fix may only be possible on one of them. If neither can be closed, the outcome is an ADR, not code.
- The new ADR is a `.starter/docs/` change, so it needs the full review cycle and a `unanimous-consensus:` line.
- The canary PR runs on the real CI accounts. It is a draft and never gets auto-merge, so it can't merge even if its checks go green.

## Notes
- Options considered: Azure step `target` restrictions (the checkout step doesn't take them, though a script step does, which the fallback in criterion 3 could use); `attr.tree` plus submodule settings, which the plan picks; or documenting the residual, which is criterion 7's last resort.
